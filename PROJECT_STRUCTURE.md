# Структура проекта Corporate RAG

Этот документ объясняет проект с нуля: какую задачу он решает, где находится каждая часть, как проходит запрос пользователя и какие файлы менять для типовых доработок.

## 1. Что это за проект

`corporate-rag` — локальная RAG-система для поиска по внутренним PDF-документам и формирования ответа с помощью локальной языковой модели.

RAG расшифровывается как Retrieval-Augmented Generation — «генерация с дополнением найденным контекстом». Система сначала находит подходящие фрагменты документов, а затем передаёт только эти фрагменты языковой модели Qwen. Поэтому ответ строится не только на знаниях модели, но и на содержимом загруженных документов.

Система работает локально и состоит из четырёх основных частей:

1. Flask-приложение показывает веб-интерфейс и принимает запросы.
2. Модуль безопасности проверяет пользователя, роль, уровень доступа и ACL документа.
3. Поисковый модуль ищет фрагменты одновременно через BM25 и FAISS, затем объединяет результаты методом RRF.
4. Локальная Qwen формирует итоговый ответ и указывает использованные источники.

Главный адрес после запуска: `http://127.0.0.1:8502`.

Вход пользователей — `/login`. Вход администратора разделён на `/admin/login`
и `/admin/verify`; `/admin/cancel` отменяет незавершённую попытку. Маршруты находятся
в `rag_roles/server.py`, страницы — `templates/login.html`, `admin_login.html`,
`admin_verify.html`. Состояние после одного пароля не даёт доступа к защищённым
страницам или API.

`rag_roles/admin_auth.py` отвечает за 600-секундные коды, промежуточные попытки,
лимиты и атомарное подтверждение. `rag_roles/admin_access.py` — только локальная
CLI-генерация с тем же `RAG_ROLES_DATA`. `sessions.py` проверяет версию, роль,
серверное подтверждение второго этапа и время бездействия.

Дополнительные таблицы: `admin_codes` (хеш и жизненный цикл кода),
`admin_login_attempts` (первый этап, срок и ошибки), `admin_code_checks` (устойчивый
лимит по пользователю), `security_migrations` (однократное включение механизма).
В `user_sessions` хранятся роль при входе и `admin_verified_at`. Триггер
`revoke_changed_auth` отзывает сессии, незавершённые входы и коды при изменении
полей безопасности пользователя. `storage.py` создаёт согласованную SQLite-копию
перед первой миграцией заполненной базы. Коды, пароль и идентификаторы сессий
в журнал не записываются. Тесты механизма — `tests/test_admin_auth.py`.

Просмотр источников: `rag_roles/pdf_sources.py` находит оригинальные PDF по записям
`document_files` или `imported_sources` и формирует изображение физической страницы
из `metadata.pdf_page`. Маршруты `/documents/<id>/sources/<chunk_id>`,
`/documents/<id>/sources/<chunk_id>/page.png` и `/documents/<id>/pdf` в `server.py`
проверяют актуальный доступ. Страница просмотра — `templates/source.html`;
ссылки из результатов поиска и карточки документа — `templates/page.html`.
Проверки — `rag_roles/tests/test_pdf_sources.py`. Оригинальные PDF не изменяются.

## 2. Общая архитектура

```text
Браузер пользователя
        │
        ▼
rag_roles/server.py                 Flask, сессия, маршруты, CSRF, роли
        │
        ├── rag_roles/security.py   проверка роли, ACL и уровня документа
        ├── rag_roles/storage.py    чтение разрешённых чанков из SQLite
        └── rag_roles/backend.py    безопасный адаптер к RAG-ядру
                    │
                    ▼
             app/rag_service.py     поиск и генерация на разрешённом корпусе
                │             │
                ▼             ▼
 app/search_hybrid.py     app/chat_hybrid.py
 BM25 + FAISS + RRF       промпт + локальная Qwen
                │             │
                └──────┬──────┘
                       ▼
              ответ + список источников
```

Ключевая граница безопасности находится до поиска: закрытые документы не попадают ни в BM25, ни в FAISS, ни в контекст Qwen.

## 4. Что делает каждый основной модуль

### `rag_roles/server.py` — центр приложения

Это главный исполняемый файл. Функция `create_app()`:

- создаёт Flask-приложение;
- открывает SQLite-базу;
- создаёт таблицы при первом запуске;
- применяет миграции из `storage.py`;
- загружает пользователя из сессии;
- проверяет CSRF для всех POST-запросов;
- проверяет разрешения на страницы;
- обслуживает HTML и JSON API;
- запускает поиск и сохраняет историю;
- ведёт аудит;
- отдаёт безопасные HTTP-заголовки.

При прямом запуске файл поднимает Waitress на `127.0.0.1:8502`. Опция `--init-admin` создаёт первую учётную запись администратора.

### `rag_roles/security.py` — единая политика доступа

Файл содержит:

- перечень пяти ролей;
- названия трёх уровней документов;
- допуск каждой роли;
- доступные каждой роли разделы интерфейса;
- функцию `allowed(user, document)`.

Для обычного пользователя доступ к документу появляется только когда одновременно выполнены два условия:

1. код роли присутствует в ACL документа;
2. уровень документа не выше допуска роли.

Администратор видит все документы. Неизвестные роли, повреждённый ACL и неактивный пользователь обрабатываются по принципу fail closed — доступ запрещается.

### `rag_roles/storage.py` — схема расширений и корпус

Модуль добавляет к базовой схеме таблицы для метаданных чанков, векторов, файлов и версии корпуса. Триггеры увеличивают `corpus_revision` после важных изменений.

Функция `chunks_for()` получает чанки только для уже разрешённого набора документов. Функция `public_source()` удаляет бинарный вектор перед отправкой источника в браузер.

Здесь же находится идемпотентная миграция старых ролей:

- `RAG_RESTRICTED_USER` → `RAG_ACCOUNTANT`;
- `RAG_CONTENT_MANAGER` → `RAG_REPORTING_SPECIALIST`.

### `rag_roles/backend.py` — тонкий адаптер

Этот файл не реализует второй поисковый движок. Он импортирует рабочие функции из `app/rag_service.py` и добавляет подготовку векторов при публикации документов.

Важно: на вход адаптеру должны передаваться уже разрешённые записи из базы.

### `app/rag_service.py` — рабочая RAG-служба

Модуль лениво загружает две тяжёлые модели:

- `SentenceTransformer` для эмбеддингов;
- `llama_cpp.Llama` для Qwen в формате GGUF.

Он строит временные BM25 и FAISS только по разрешённым чанкам конкретного запроса. Затем вызывает функции из `search_hybrid.py` и `chat_hybrid.py`.

Модели кэшируются в памяти процесса. Отдельные блокировки защищают кодирование и генерацию от одновременных конфликтующих вызовов. Общего кэша ответов нет.

### `app/search_hybrid.py` — поиск

Поиск состоит из трёх шагов:

1. FAISS ищет семантически похожие векторы.
2. BM25 ищет совпадения слов и терминов.
3. Reciprocal Rank Fusion объединяет два рейтинга.

Для эмбеддингов используется `intfloat/multilingual-e5-small`, размер вектора — 384. Документы кодируются с префиксом `passage:`, запрос — с префиксом `query:`.

### `app/chat_hybrid.py` — ответ Qwen

Модуль:

- превращает найденные чанки в контекст;
- формирует системные инструкции и вопрос;
- вызывает локальную модель;
- разбирает ссылки на источники в ответе;
- выбирает источники для показа пользователю.

Перед генерацией `rag_service.py` проверяет, что промпт помещается в контекст 4096 токенов.

### `rag_roles/ingestion.py` и `app/ingest_pdf.py` — обработка PDF

`rag_roles/ingestion.py` — вход для загрузки из веб-интерфейса. Он проверяет, что PDF не зашифрован, содержит от 1 до 500 страниц и имеет извлекаемый текст.

Если документ соответствует структуре казначейских PDF, используется подробный парсер из `app/ingest_pdf.py`. Для обычного текстового PDF применяется универсальный постраничный разбор. Скан без текстового слоя сначала требует OCR.

### `app/build_index_pdf.py` и `rag_roles/import_existing.py`

Это разные этапы:

- `build_index_pdf.py` создаёт исходную пару `faiss_pdf.index` + `metadata_pdf.json` из `chunks_pdf.json`;
- `import_existing.py` один раз переносит эту пару в рабочую SQLite-базу, сохраняя векторы и метаданные.

Импорт не перезаписывает исходные JSON и FAISS. Новые импортированные документы получают уровень `restricted` и пустой ACL, поэтому до назначения прав доступны только администратору.

## 5. Как проходит поисковый запрос

```text
1. Пользователь отправляет вопрос
2. server.py проверяет сессию, роль, CSRF и параметры
3. visible_docs() исключает запрещённые документы
4. chunks_for() читает только чанки разрешённых опубликованных документов
5. backend.retrieve() запускает BM25 + FAISS + RRF на этом наборе
6. server.py повторно сверяет найденные id с доверенным набором
7. backend.generate() передаёт выбранные фрагменты Qwen
8. Перед и во время генерации проверяются пользователь и версия корпуса
9. В историю записывается вопрос, в аудит — событие и id источников
10. Браузер получает ответ и безопасные метаданные источников
```

Повторные проверки версии нужны на случай, если администратор изменил роль, ACL или корпус прямо во время долгого запроса. В этом случае результат отклоняется с HTTP 409, а не показывается со старыми правами.

## 6. Роли и доступные разделы

| Код роли | Название | Основные возможности |
|---|---|---|
| `RAG_USER` | Обычный пользователь | Поиск, личная история, общие документы из ACL |
| `RAG_ACCOUNTANT` | Бухгалтер | Поиск, история, разрешённые документы, фильтр уровня |
| `RAG_REPORTING_SPECIALIST` | Специалист по отчётности | Поиск, история, разрешённые документы, фильтр уровня |
| `RAG_ADMIN` | Администратор | Все разделы, пользователи, ACL, загрузка, публикация, удаление, настройки |
| `RAG_SECURITY_AUDITOR` | Специалист по ИБ | Поиск, история, разрешённые документы, аудит и события безопасности |

ACL хранится в поле `documents.roles` как JSON-массив кодов ролей. Пустой массив означает, что документ видит только администратор.

## 8. Структура SQLite-базы

Главная база: `rag_roles/data/roles.sqlite3`.

| Таблица | Что хранит |
|---|---|
| `users` | логин, имя, хеш пароля, роль, активность |
| `documents` | название, уровень, ACL, статус публикации |
| `chunks` | текстовый фрагмент, документ, страница |
| `chunk_details` | JSON-метаданные и бинарный embedding чанка |
| `document_files` | путь к сохранённому загруженному PDF |
| `history` | вопросы пользователей; ответы не сохраняются |
| `audit` | события, актор, объект, статус, время UTC и IP |
| `user_sessions` | версия пользователя, роль при входе, IP, активность, подтверждение второго этапа |
| `admin_codes` | хеш кода, пользователь, версия, создание, срок, использование и отмена |
| `admin_login_attempts` | ожидание второго этапа, число ошибок, завершение и отмена |
| `admin_code_checks` | проверки за скользящие 600 секунд для каждой учётной записи |
| `security_migrations` | однократные миграции безопасности |
| `attempts` | неудачные входы для ограничения перебора паролей |
| `settings` | глобальные `top_k` и `temperature` |
| `imported_sources` | контроль повторного импорта старого корпуса |
| `corpus_revision` | версия корпуса и прав для защиты долгих запросов |

Связи:

```text
users ──< history

documents ──< chunks ─── chunk_details
     │
     ├────── document_files
     └────── imported_sources
```

Удаление записи документа каскадно удаляет его чанки, метаданные и запись пути. Сам сохранённый PDF физически не удаляется.

## 9. Формат документа и чанка

Минимальные рабочие поля чанка:

```json
{
  "chunk_id": 123,
  "source": "appendix_1.pdf",
  "document_title": "Название документа",
  "document_page": 15,
  "pdf_page": 18,
  "section": "Раздел",
  "subsection": "Подраздел",
  "point": "1.2",
  "subpoint": "1.2.1",
  "text": "Текст фрагмента"
}
```

Не каждый чанк обязан иметь все структурные поля. Для обычных PDF часть полей остаётся пустой. В SQLite основной текст и страница лежат в `chunks`, расширенные поля — JSON в `chunk_details.metadata`, embedding — BLOB в `chunk_details.vector`.

## 10. Интерфейс и шаблоны

В приложении используется один светлый Flask/Jinja-интерфейс. Старый Streamlit отключён и сохранён только в архиве.

- `base.html` задаёт боковое меню, шапку и общий layout.
- `page.html` содержит условные секции для поиска, истории, документов, загрузки, индексации, пользователей, настроек, аудита и системной страницы.
- `login.html` содержит форму входа.
- `error.html` показывает контролируемые ошибки.
- `style.css` отвечает за цвета, сетку, таблицы, формы и мобильную адаптацию.

Внешние JavaScript-библиотеки не используются. Content Security Policy запрещает сторонние скрипты и встраивание приложения во фрейм.

## 11. Конфигурация через переменные окружения

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `RAG_ROLES_DATA` | `rag_roles/data` | каталог SQLite, ключа и загрузок |
| `RAG_HTTPS` | не задана | при `1` включает флаг Secure у cookie |
| `RAG_EMBEDDING_MODEL` | `intfloat/multilingual-e5-small` | embedding-модель |
| `RAG_MODEL_PATH` | `models/Qwen3-8B-Q4_K_M.gguf` | путь к GGUF-модели Qwen |

Embedding-модель загружается только из локального кэша (`local_files_only=True`). Замена embedding-модели без полного пересчёта сохранённых векторов недопустима.

## 13. Жизненный цикл нового документа

```text
Администратор загружает PDF
        │
        ▼
ingestion.py проверяет и разбивает его на чанки
        │
        ▼
SQLite: документ получает статус «Ожидает индексации»
        │
        ▼
Раздел «Индексация» вызывает backend.prepare_index()
        │
        ▼
Создаются embeddings, проверяются размерность и конечность чисел
        │
        ▼
Одна транзакция сохраняет векторы и статус «Готов»
        │
        ▼
Документ участвует в поиске только для ролей из ACL с нужным допуском
```

Если подготовка индекса завершается ошибкой, публикация не происходит и прежний рабочий корпус остаётся доступен.

## 15. Важные ограничения и правила безопасности

- Нельзя фильтровать закрытые источники только после поиска: ACL обязан применяться до BM25, FAISS и Qwen.
- Нельзя создавать общий кэш ответов только по тексту вопроса: у пользователей разные права.
- Нельзя передавать `vector` в ответ API.
- Нельзя публиковать `session.key`, SQLite-базу, внутренние PDF и локальные модели.
- Нельзя менять embedding-модель без пересчёта всех embeddings.
- Нельзя считать файлы из `.archive/` рабочим кодом: это снимки для восстановления.
- Нельзя запускать старый Streamlit как основной UI: актуальный интерфейс находится в `rag_roles/templates/`.
- При изменении ролей, ACL или корпуса во время генерации текущий запрос должен завершиться конфликтом, а не вернуть устаревший ответ.
- Сохранённый PDF после удаления документа из БД остаётся на диске; при необходимости его удаляют отдельно и осознанно.
