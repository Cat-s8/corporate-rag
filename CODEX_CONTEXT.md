# Контекст проекта `corporate-rag`

## Обновление входа администратора — 9 октября 2026

Пользователь запросил двухэтапный вход: `/admin/login` (пароль), затем
`/admin/verify` (одноразовый локальный код). Обычный `/login` не выдаёт сессию
администратора. До проверки кода есть только серверная промежуточная попытка,
а серверный признак второго этапа хранится в `user_sessions.admin_verified_at`.

Локальная утилита: `rag_roles/admin_access.py generate --login admin` через
корневое `.venv`. Код — 16 символов, 80 бит, 600 секунд с генерации, один раз;
хранится только хеш. Проверка и выдача сессии атомарны. Пять ошибок закрывают
попытку; SQLite хранит общий лимит 10 проверок за 600 секунд на пользователя.
`admin_auth.py` реализует коды и попытки; `storage.py` — миграцию, резервное
копирование SQLite и отзыв при изменениях учётной записи. Первый запуск
миграции отзывает старые административные сессии, повторный — нет.

Перед миграцией заполненной рабочей базы автоматически создаётся проверенная
копия в `<RAG_ROLES_DATA>/backups/roles-before-admin-2fa-*.sqlite3`.
В этой задаче проверки выполняются на временных БД. Фактический запуск на рабочей
БД следует отличать от успешных тестов; результаты — `rag_roles/VERIFICATION.md`.
Независимость второго фактора зависит от отдельно защищённого доступа к ОС.
RDP/удалённая командная строка позволяют выполнить локальную утилиту; физическое
присутствие она не доказывает. Права Windows и Tailscale автоматически не менять.

Ранее добавлены серверный idle timeout (admin 5 минут, остальные 15), IP сессии
в аудит/CSV, история запросов пользователей для администратора, отзыв сессий при
удалении с сохранением истории, запрет назначения admin через веб-формы,
карточки учётных записей и индикатор генерации. Десятиминутный срок кода не
ограничивает уже подтверждённую активную сессию.

## Цель диплома

Разрабатывается локальная RAG-система для документации Казначейства Свердловской области.
Специальность: «Информационно-аналитические системы безопасности» (УрФУ).
Система должна работать офлайн / в локальном контуре и давать ответы с указанием
исходного документа и страницы.

## Текущая RAG-часть

- Активная локальная модель: `Qwen3-8B-Q4_K_M.gguf` через `llama-cpp-python`. Qwen2.5-3B сохранена как альтернативная модель.
- Эмбеддинги: `intfloat/multilingual-e5-small`.
- Векторный поиск: FAISS (`IndexFlatIP`).
- Лексический поиск: BM25.
- Веб-интерфейс и гибридный поиск уже существуют; перед правками необходимо
  самостоятельно найти реальные точки входа и форматы данных в этом репозитории.
- Обработаны документы `appendix_1.docx`, `appendix_2.docx`, `appendix_3.docx`,
  `quide.docx`; ранее было около 192 фрагментов. Эти цифры не считать гарантией —
  проверить актуальное состояние файлов.
- В результатах должны показываться источник и номер страницы.

## Требуемое расширение: роли и безопасность

Добавить к существующему RAG серверное разграничение доступа, не отдельную
демонстрационную замену RAG.

Роли:

| Код | Роль | Функции |
|---|---|---|
| `RAG_USER` | Обычный пользователь | Поиск и личная история, только общие разрешённые документы |
| `RAG_ACCOUNTANT` | Бухгалтер | Поиск, фильтры и чтение разрешённых документов |
| `RAG_REPORTING_SPECIALIST` | Специалист по отчётности | Поиск, фильтры и чтение разрешённых документов |
| `RAG_ADMIN` | Администратор | Пользователи, роли, настройки, все документы, загрузка, публикация и удаление |
| `RAG_SECURITY_AUDITOR` | Специалист по ИБ | Аудит, события безопасности, CSV-выгрузка; не управление системой |

Политика доступа к документу: для неадминистратора роль должна быть в ACL
документа **и** уровень документа не должен превышать допуск роли.

Уровни: `general`, `internal`, `restricted`.

Критическое правило: ACL-фильтрация выполняется **до** BM25, FAISS, формирования
контекста и вызова Qwen. Нельзя передавать модели закрытый фрагмент, а потом
скрывать ответ. Нельзя использовать кэш ответа, общий для разных ролей, только
по тексту вопроса.

## Уже подготовленный отдельный модуль

В архиве `rag_roles_diploma.zip` есть прототип ролей на Flask/SQLite:

- `server.py` — вход, RBAC, документы, аудит;
- `backend.py` — адаптер поиска и генерации;
- `templates/`, `static/` — интерфейс;
- `tests/test_access.py` — 16 проверок доступа.

Это **не готовая интеграция** с текущим RAG: она требует сопоставления реальных
форматов существующих `chunks`, BM25, FAISS и вызова Qwen. Не заменять текущий
веб-интерфейс этим модулем целиком без анализа.

## Актуальное решение: один светлый интерфейс

По прямому запросу пользователя тёмный Streamlit отключён и перенесён в
`.archive/single-interface-2026-09-23/`. Единственный рабочий интерфейс —
Flask/Jinja `rag_roles/templates` на http://127.0.0.1:8502.
Поиск, история, роли, документы и аудит работают в нём с одним входом.
`start.ps1` больше не запускает Streamlit. Прежняя обёртка `app/start_ui.bat`
позже убрана в архив при уборке 24 сентября.
Ранее записанное требование сохранять Streamlit как основной UI заменено
этим решением пользователя. BM25/FAISS/Qwen и проверки ACL сохранены.


## Замена ролей по запросу пользователя

Бизнес-роли — бухгалтер (`RAG_ACCOUNTANT`) и специалист по отчётности
(`RAG_REPORTING_SPECIALIST`). Изменять документы может только администратор.

и ACL при запуске сервера; миграция идемпотентна. Пустой ACL не расширяется.
Резервная копия перед заменой: `.archive/business-roles/`.
